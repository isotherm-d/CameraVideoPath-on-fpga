# v36 候选：短帧后持续拼帧与 AE 慢速振荡修复

用户在 v35 上板后报告竖向错位接缝和慢速 AE 闪烁：关闭 AE 后闪烁停止，接缝仍然存在。[截图](board_issue_evidence.png)显示 30fps、完整率 100%、平均亮度 110、曝光 984 半行、模拟增益 108、流错误 3、最近异常 RAW 组数 230270（应为 230400）、最近输出帧长度错误。

## 确认的错误与修复

### 1. 短帧造成持续的网络拼帧

旧发送器在新 SOF 时重置帧内字节计数，却没有取消前一帧未满的字节块；MAC 按固定包数维护帧号和偏移，因此下一帧的数据被接到旧帧尾。即使之后输入恢复完整，旧帧包序和 FIFO 数据仍不匹配，错误会延续。UDP 包 CRC 正确、PC 收齐一组包并不证明这些包属于同一个真实输入帧，故截图中的 100% 完整率不能排除此错误。

已独立复现：完整帧→缺尾帧→两帧完整输入，v35 出现 **272 处帧号/像素不匹配**，最后一帧也没有完整发送；（原始日志已清理）。

截图异常帧少 130 组，对应 520 像素。旧发送器从后续帧补齐缺失数据，会把后续帧的起点推迟 520 像素，从而在约第 760 列（1280−520）形成持续接缝；这个推断与截图中接缝的位置相符。

修复为每个完整字节块携带帧号和本帧偏移；新 SOF 到来时，之前未满块产生带长度的“丢弃描述符”，MAC 排空这些残留字节而不发包、不消耗整包信用。之后的新帧重新从自己的偏移 0 发送。描述符队列预留读流水空间并施加背压，防止元数据先溢出。原 UDP 6000 应用头、完整帧像素和 CRC 协议保持。

### 2. 原生帧起点不能由像素计数回绕推导

旧 `uial2axis` 用 hcnt/vcnt 同时为零产生 SOF，帧内多余数据可在计数回绕时再造一帧；原生 start 与首组 valid 同拍时也未正确消费首组位置。现在只使用 CSI 原生 start，消隐期先锁存 pending，首个有效组携带 SOF，同拍 start/valid 也正确处理。`line_retimer` 仍按 320×720 截取，余量不再伪造帧。

这是帧边界代码中的确定错误；截图中最初少 130 组的全部物理成因仍不能仅凭现有诊断确认，可能涉及边界或输入丢失。v36 对缺组帧不再污染之后的完整帧，保留 RAW/输出错误诊断，并需要上板观察它们是否继续增长。

### 3. 平均亮度目标与高光保护争夺控制

v35 在高光比例超过 5% 时降低曝光，随后亮度低于 104 又向均值 112 拉回。高反差场景可能无法同时满足两个条件，于是一直循环。此前均匀静态光照测试没有覆盖这个约束冲突，本次用 80% 暗区域＋20% 亮区域的闭环模型复现。

v36 保留 PID、四帧平均、两帧等待、曝光优先和 1～4 倍数字增益；高光约束触发时降低并保留可达的保护亮度目标，不再反复回拉到 112。默认目标仍为 112，保护目标范围 32～112；实测均值相对保护目标变化超过 24 个亮度码且无过量高光时，判定场景明显改变，清历史并恢复默认目标。关闭 AE、手动取消或手动设置成功提交也重置目标。普通无高光场景的原死区与响应保持。

闭环最后 120 帧，旧版仍调节 **15 次**，新版调节 **0 次**；新版曝光 406、均值 87、保护目标 83、剪裁像素 0。场景变成均匀暗场后，新版恢复目标 112，并收敛为曝光 1800、数字增益 Q8=772、均值 108。（原始日志已清理）。这是模型验证，不代替当前实机的光照/噪声曲线验证。

高光优先时，平均亮度可以低于原来的 112，这个取舍用来保留高光并避免控制振荡；没有把模拟增益重新加入自动分配。

### 4. SC500CS 曝光/增益按组提交

原表逐个写 0x3e00/01/02 与 0x3e08/09。依据本地 SC500CS V1.8 手册第 2.3 节，改为：0x3817=0x20（N=0）、0x3800=0x00（group0 开始）、五个曝光/增益寄存器、0x3800=0x10（结束）、0x3800=0x40（下一帧指定时刻生效）。总计 9 次写。此芯片文档使用 **0x3800**，不是其他 SmartSens 型号常见的 0x3812。

原 I2C 重试/失败与确认机制保留；成功写完不等于像素立即体现新曝光，仍保留两帧保护。真实 I2C 序列和独立传感器 group 模型检查确认部分曝光字节不会提前成为活动参数；启动/运行写入、NACK、超时及手动设置回归通过。（原始日志已清理）、（原始日志已清理）。

## 上位机与兼容

V27 64 字节扩展的 flags bit0 和原 16bit reserved 字段报告硬件构建号 36 与实际 AE 目标亮度。协议长度及原字段不变，旧客户端仍可收图。新版上位机增加“硬件 v36；AE 目标亮度”一行；下载后需重启正在运行的收图窗口以加载新版 Python 文件。高光保护模式下请看实际目标，不能仅以均值是否达到 112 判断收敛。

- **41 项 RTL、2 组网络包完整性、38 项 Python 测试通过**。41 项包括新增 4 项问题场景测试及重新加入的摄像头启动回归。
- 网络测试覆盖缺尾、整包边界截断、小于一包的帧、多余数据、连续 64 个短帧及随后完整帧；27 个发出包的帧号、偏移、每个像素字节全部匹配，没有描述符溢出，最后健康帧完整发送。
- 原生 SOF 测试：正常、同拍 start/valid、额外数据、短帧后正常帧，得到 45 个有效组、3 个真实 SOF；旧计数实现同激励产生 5 个 SOF。
- 普通静态场景 PID 仍为暗/亮/极暗 47/47/95 帧进入目标区，460 帧实际视频控制链路仍通过。`tb_v26_pid_timing` 明确是冻结 v34→v35 的历史时序差分，新 AE 行为通过当前控制器和高反差闭环单独验证；不声称新高光策略与旧版逐拍等价。

## 上板检查

[v36 候选比特流](camera_network_only_v36_frame_ae_fix_candidate.bit)。助手没有写入 SRAM/Flash；历史比特流保留。

1. 加载候选并重启收图窗口，确认状态出现“硬件 v36”。先关 AE 确认接缝不再持续，查看流错误是否继续增长。
2. 在相同静止场景打开 AE，等待收敛后观察曝光和数字增益是否还周期往返；高光保护时目标可能小于 112。
3. 遮挡/恢复或换均匀场景，确认目标和曝光能够重新调整。若仍有异常，保留目标、均值、曝光、数字增益、RAW 组数及输出帧错误诊断继续定位。
