# v33 候选：恢复瞬态流错误后的显示

用户反馈 v32 加载后有正常帧率但全黑。[截图](black_screen_evidence.png)显示平均亮度 137、AE 关闭、曝光 1800 半行、增益 108 档、初始化及 I2C 写入正常，累计流错误 2。

## 已确认的直接原因

`cvp_advanced` 遇到任意流错误将 fault 置 1，只有复位才能清零；上位机 `cam_gui_v26.App.update` 收到此标志就执行 `frame[:]=0`。因此后面的完整、有亮度的帧仍被程序涂黑，同时 AE/AWB 也因 fault 保持关闭。截图与代码共同定位到这个永久锁存行为。

原始两次流错误的来源尚不能从旧状态包判断。v33 增加来源诊断，避免把推测当成板测结论。

## 修复

- 保留累计流错误数；fault 改为当前流状态。出现错误立即进入异常状态，随后连续两帧都有 SOF/EOF、像素数为 W×H、且没有新错误时解除 fault。错误涉及的帧不参与恢复判断，第二个恢复 EOF 与新错误碰撞时错误优先。
- 新增输出帧长度验证。缺 SOF、短帧、长帧、未结束就来新 SOF，以及持续溢出均不能解除异常。
- 在 V27 扩展原有 24 字节保留区加入 STRM 诊断；原有字段、报文长度和视频协议保持兼容。记录累计/最近错误来源、最近异常 RAW 组数、输出帧号及像素数。
- 上位机显示当前流状态与错误来源。等待恢复期间仍置黑；恢复后显示完整帧。已有上位机也能按恢复后的 fault 标志继续显示，重启新版上位机可看到新增诊断。
- v32 的 AE 四帧平均、约 3.125% 曝光步长和 2 档增益步长保留。本次没有改曝光默认值、传感器表或像素计算。

诊断位：bit0 RAW组数，bit1 RGB帧边界，bit2 风格缓存，bit3 亮度统计，bit4 网口缓存，bit5 输出帧长度。1280×720 的 RAW 每帧应为 230400 组、输出应为 921600 像素。

## 验证

30 项 RTL 仿真、两组独立网络包 CRC/IP/UDP 校验、36 项 Python 测试全部通过。

- 旧版复现：第一帧采集计数少一组，之后六帧像素输出正常、累计错误仅 1，但旧 fault 永久保持。
- 新旧完整图像核心对比：输入相同六帧，逐拍像素、valid、SOF/EOF、帧号一致；旧版保持 fault，新版正常帧恢复后解除 fault，累计错误仍为 1，诊断记录异常组数 31（测试分辨率 16×8，每帧应为 32 组）。基准源码冻结在 `tools/sim/gold_v32/`，哈希与 v32 manifest 一致。
- 流健康模块 33 项检查：五类输入错误、输出长度、两帧恢复、缺 SOF、短/长/中断帧、第二恢复 EOF 与错误碰撞、持续错误和复位。
- 既有 AE、中值、风格、对比度、RAW 旁路及网络差分/集成测试均通过；诊断解码测试确认旧报文兼容及新字段偏移。
